# 生命周期资源所有权设计

## 背景

生命周期修复的前三轮已经解决了启动单飞、关闭并发、状态保存失败回滚和部分失败重试，但独立复核仍发现三个同源缺口：浏览器停止会在确认终止前移除句柄；Bridge 在代理登记前失败时缺少节点所有权；日志代理停止只等待监听线程，不等待仍可能写入流量的连接线程。

根因不是三个孤立条件，而是资源所有权分散：登记表既被当作“活动索引”，又被当作“清理责任凭证”，不同路径对何时撤销登记没有统一约束。

## 已选方案

采用小范围所有权重构，不改变 HTTP API、状态文件结构或正常使用流程。

### 1. 统一所有权规则

- 进程、代理或连接一旦登记，只有在确认终止后才能撤销登记。
- 终止失败必须保留原始对象引用，使公开停止、退出清理或下一次重试仍能找到它。
- 条件删除必须同时校验键和对象身份，避免删除并发替换后的新对象。
- Bridge 的所有权从核心进程创建成功时开始，而不是从日志代理创建或状态文件保存成功时开始。

### 2. Bridge 运行时所有权

- 新增内存表 `BRIDGE_NODE_TABLE: dict[str, str]`，记录 `bridge_id -> node_id`。
- 核心进程写入 `PROCESS_TABLE` 时，在同一个 `PROCESS_LOCK` 临界区登记节点所有权。
- 同节点启动前检查 `BRIDGE_NODE_TABLE`；只存在核心进程、尚未存在日志代理的残留也必须阻止重复启动。
- `stop_process()` 分别停止代理与核心进程；成功的资源才按对象身份移除。只有该 Bridge 已无进程、无代理时才移除节点所有权。
- 现有 `PROCESS_TABLE`、`LOG_PROXY_TABLE` 和状态文件保持兼容，不做跨文件迁移。

### 3. 浏览器进程所有权

- `stop_browser_instance_process()` 先读取句柄，成功终止后再从实例表和节点表中条件删除。
- 节点级未跟踪浏览器停止会尝试全部句柄：成功项删除，失败项保留；失败汇总后向调用方抛出。
- 状态记录只有在对应停止操作成功后才标记为 `stopped`。

### 4. 连接排空与最终流量

- `Socks5LogProxy` 显式跟踪每个客户端处理线程和客户端套接字。
- `stop()` 先停止接受新连接，再关闭已登记客户端套接字以唤醒阻塞读写，然后等待所有客户端处理线程退出。
- 若在限定时间内仍有处理线程存活，`stop()` 报错并保留代理登记；shutdown 不得报告成功。
- 只有 `proxy.stop()` 成功后，`stop_process()` 才读取流量快照，因此保存的是不再变化的最终计数。

## 数据流与失败语义

启动顺序为：创建核心进程 → 原子登记进程及节点所有权 → 等待核心 → 创建并登记日志代理 → 保存状态。任一步失败都调用同一 `stop_process()`；终止失败时登记保留，下一次同节点启动被拒绝，shutdown 可继续重试。

停止顺序为：关闭代理监听与连接并等待排空 → 终止核心进程 → 对成功项撤销登记 → 读取稳定流量 → 保存停止状态。浏览器遵循相同的“终止成功后撤销登记”规则。

## 测试要求

新增回归测试必须先在旧实现上出现预期失败，再实施生产代码：

1. 浏览器 terminate 失败后两张进程表仍保留句柄，第二次停止会重试；节点级停止不会丢失失败或尚未处理的句柄。
2. Bridge 在日志代理创建前失败且核心 terminate 失败时，节点所有权仍存在；第二次启动不创建新进程，shutdown 成功后所有权才移除。
3. `Socks5LogProxy.stop()` 在客户端处理线程退出前不返回；处理线程退出前写入的最后流量包含在 shutdown 持久化快照中。
4. 既有生命周期测试和完整 Python 测试套件保持通过。

## 非目标

- 不把全部运行时表替换成新的大型管理器或持久化运行时注册表。
- 不改变 API 请求/响应、状态文件字段、端口选择、浏览器 Profile 或核心启动参数。
- 不为终止失败增加无限重试；失败保持显式并由现有再次停止或 shutdown 路径重试。
